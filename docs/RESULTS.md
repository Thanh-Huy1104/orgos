## What we built

**v2 async scrum team.** Five roles running as independent asyncio tasks with heartbeat schedules, pulling work from a shared filesystem board through a rebase-before-merge queue. All coding delegated behind a `CodingExecutor` Protocol so any of `claude -p`, `copilot -p`, or LiteLLM-backed `spawn` can drive the actual code changes. On top of that, real Scrum machinery: paired test subtasks enforcing Definition of Done, time-boxed sprints with commitment, and a PO acceptance gate between merge and done.

**Waterfall baseline retained.** The sequential PO → Architect → Test → DevSecOps pipeline (the topology an LLM produces by default when asked for "an agentic dev team") still ships. Comparison harness runs both against the same goal + model so the topology difference is the only variable.

## What we measured

Five progressive comparison runs on `/tmp/flask-target` (minimal Flask app) with DeepSeek Chat via `spawn` for both topologies (fair, same model). Each run tightened one variable.

| Run | Goal | Scrum config | Result |
|---|---|---|---|
| 1 | `/notes-count` endpoint | v2 async, no DoD/sprints/acceptance | Infrastructure worked. Both delivered. Scrum did more stories but at similar cost. |
| 2 | full CRUD (Notes + Projects) | v2 async, no DoD/sprints/acceptance | Scrum edged out on 6/7 axes: 10 vs 8 stories done, 2.52M vs 2.62M tokens, ~$0.02 cheaper. Waterfall produced more test files (57 vs 43). |
| 3 | full CRUD (same) | **+ DoD paired test subtasks + sprints + PO acceptance gate** | **Scrum spent 57% less money** ($0.22 vs $0.51) but delivered fewer stories (3 vs 7). Real-Scrum machinery is real overhead in a short window. |

Runs 1-2 were "async scrum, more or less"; run 3 is the first defensible apples-to-apples where scrum implements real Scrum mechanics.

### Run 3 — the honest one

Same goal, same model, same executor, ~12-min windows for both.

| Metric | Waterfall | Real Scrum |
|---|---|---|
| stories drafted | 10 | 10 |
| stories done | 7 | 3 |
| stories blocked | 3 | 3 |
| tokens in | 1.69M | **710k** (58% less) |
| tokens out | 46k | **25k** (46% less) |
| est. cost (DeepSeek Chat) | $0.51 | **$0.22** (57% cheaper) |
| wall time | 9m 26s | 12m 19s |
| tests on integration | 36 passed | 23 passed |

Both delivered working code — integration branch `pytest` passes for both.

### Where the cost gap comes from (structural, not noise)

Waterfall's linear pipeline runs Architect + Test + DevSecOps on **every** story — 3× the LLM invocations per delivered story. Scrum invokes one executor per pulled story. On the same 10-story decomposition, waterfall's ~7 done stories × 3 roles ≈ 21 LLM sessions vs scrum's ~5 executor invocations plus per-story poker + PO ceremonies ≈ 10-12 sessions total.

### Where scrum's throughput loss comes from (all three additions cost something)

1. **Sprint filter (Sprint Backlog commitment).** Sprint 1 committed 6 stories. Only those were pullable. Any un-committed ready story sat.
2. **DoD paired test subtasks (`depends_on`).** Test story blocked from pull until its parent feature was done — correct real-Scrum behavior, but sequential.
3. **PO acceptance gate.** Merged code goes to `pending_acceptance`, not `done` — requires PO's 1-minute ceremony to accept. Adds one step per story.
4. **`files_to_touch` overlap.** Paired feature+test both touch `tests/*.py` — the collision guard blocks concurrent claim. 2 `merge_conflict` events in run 3 vs the usual 1.

Sprint boundary fired once (`sprint_opened`) but the automatic close didn't reach — SM's HEARTBEAT is at 4h cadence, and the run window was 12 min. Multi-sprint compounding effects are not visible at this scale.

## What this actually tells us

**Two independent findings, both defensible:**

1. **Scrum is materially cheaper per goal (~50% on this workload).** The 3-role-per-story pattern that waterfall runs is expensive and it's the structural driver. If you care about dollar-cost per delivered story, scrum wins.

2. **Scrum's throughput advantage isn't visible in a 12-minute window.** Real Scrum's ceremonies and DoD add overhead that only pays back over many sprints — as the wiki compounds, as the PO refines the sprint backlog to fit measured velocity, as retrospective action items feed into future behavior. One window with one sprint doesn't let it compound.

**What the chapter's thesis ("scrum beats waterfall") maps to, empirically:**
- ✓ On cost per delivered feature — yes, confirmed
- Not-yet-measured on delivery-rate-over-time — needs multi-hour runs with multiple sprints
- Not-yet-measured on knowledge compounding — needs a task that references previous decisions

**What waterfall wins on:**
- Raw stories-done in a short window
- Bakes in more testing (every commit has a Test role sweep) — you get more test files whether the story needed them or not

## Known gaps in the comparison

- **n = 1 per topology.** LLMs are stochastic. Real credibility requires 3-5 runs per topology and averages. Reproducible via `scripts/run_comparison.sh`.
- **Sprint boundary is time-based, not condition-based.** SM's 4h ceremony doesn't fire in a 12-min window. To see multi-sprint behavior, either lengthen the run to 4-6h or add a `--sprint-duration-seconds` override to the SM's cadence.
- **PO acceptance gate is v1** — auto-accepts anything with a commit_sha. A stricter version would parse the commit against acceptance criteria stored on the story.
- **`files_to_touch` discipline is soft.** The PO prompt asks for it, but LLM output sometimes has feature and test both touching `tests/*.py`. Should get stricter enforcement or auto-splitting.
- **No velocity forecasting** — sprints record `points_completed` but the PO doesn't use that to right-size the next sprint's commitment.
- **No stakeholder demo** (Sprint Review in real Scrum). Only retrospective fires. PR publishing is the closest analog.

## Direction

Ranked by impact-to-effort, low-risk to high-risk:

### Immediate wins (each < 1 day)
1. **Multi-run statistics.** Wrap `run_comparison.sh` to loop N times per topology and emit mean/stddev in the HTML. Gets us defensible n≥5 comparisons.
2. **SM sprint cadence knob.** `--sprint-duration-seconds` on `orgos start` so demo/CI runs can see 3-4 sprints in a short window without editing HEARTBEAT.md.
3. **Velocity-informed replan.** PO's replan reads previous sprint's `points_completed` and right-sizes the next sprint's commitment.

### Meaningful features (1-3 days each)
4. **Enforce `files_to_touch` non-overlap in the decomposer.** Post-process PO output: if feature and test share files, split test file path (`tests/test_<feature_slug>.py`).
5. **Stricter PO acceptance.** Read the commit diff and check against a per-story `acceptance_criteria: list[str]` field. New Story field, new PO prompt rule.
6. **Longer horizon comparison.** Run the harness on a real project for a full day (say `orgos start --timeout-seconds 14400` = 4h) with a bigger goal. That's where scrum's compounding should show.

### Bigger direction
7. **Dogfood.** Point orgos at itself for a real feature (one of the items above). Highest-signal test — real code, real quality bar, real failure modes.
8. **Second sprint-topology.** Kanban (no sprints, just WIP limits) as a third topology to compare against. Would tell us whether the "sprint" structure or the "board" structure is the dominant factor.
9. **Non-code goals.** Docs, analysis, RCA — see if the topology gap holds when the task isn't shipping tests-passing code.

### Explicit non-goals for now
- Reimplementing Claude Code / Copilot tool suites inside `spawn`. If a user wants the full agentic tool loop, use the vendor's executor.
- Multi-process board sharing. The whole runtime is single-process by design.
- Distributed team simulation. Real Scrum is co-located, we're modeling one team.

## For a recipient wanting to reproduce

Every result above is regenerable from a clean checkout:

```bash
git clone <this repo>
cd orgos
pip install -e ".[dev]"
pytest -q                        # full suite, ~200 tests, ~30s

# Bootstrap a minimal target
mkdir /tmp/flask-target && cd /tmp/flask-target
git init -q
# ... (see README §3 for the create script)

# Point at your LLM: claude/copilot subscription OR DeepSeek/OpenAI key in .env
# ... (README §2)

# Run the comparison
cd -
scripts/run_comparison.sh --repo /tmp/flask-target \
    --goal "Add /notes-count GET endpoint returning {count: N}" \
    --model deepseek/deepseek-chat --executor spawn \
    --scrum-seconds 480
# → /tmp/orgos-comparison.html
```

Cost is ~$0.20-$0.50 per comparison run on DeepSeek Chat, less if you use `claude` or `copilot` subscription executors.
