1. Overview — two layers, three topologies

orgos is two software layers:

  • Agile team (top layer, orgos/agile/) — the topology that runs against a goal. Two implementations ship: async Scrum (v2, default) and sequential Waterfall (baseline for comparison).
  • Spawn/governance substrate (bottom layer, orgos/spawn/) — how individual agents are actually invoked, tier-enforced, tool-gated, audited, and rubric-graded. This layer is OFF-LIMITS to changes made by agents themselves — it's the platform's safety fabric.

                                  │

2. Agile runtime (v2 async scrum)

Five roles run as independent asyncio.Tasks under a shared TeamSupervisor. No dispatcher. Each agent reads its own HEARTBEAT.md for a natural-language schedule ("Every 30 seconds", "Every 4 hours") and either pulls from the board (delivery agents) or runs scheduled ceremonies (coordination agents).

3. Coding executors — pluggable LLM backend

Actual coding is delegated behind a CodingExecutor Protocol so the async runtime doesn't hard-code any LLM vendor. Three implementations ship. The CLI auto-picks in this order.

ExecutorHowAuth
ClaudeCodeExecutor Shells to claude -p <prompt> (Claude Code print mode) User's Claude subscription. No API key handled by orgos.
CopilotCliExecutor Shells to copilot -p <prompt> (GitHub Copilot CLI) User's GitHub Copilot subscription. No API key handled by orgos.
SpawnCodingExecutor Uses orgos.spawn + LiteLLM (CrewAI-based worker + BashTool) Whatever API key or OpenAI-compatible URL you point LiteLLM at (DeepSeek is the cheapest).

Success criterion for any executor: HEAD advanced past the pre-run baseline inside the given worktree. If not, the story transitions to blocked and the executor's .error field records why.

Design note: The SpawnCodingExecutor path is deliberately not feature parity with Claude Code / Copilot — it uses only BashTool (no native Read/Edit/Grep tools). For bite-sized stories that's sufficient. If you want the vendor's full agentic tool suite, use the vendor's executor.

4. Board — filesystem-backed state machine

All coordination happens through <workspace>/board/. No shared memory, no queues in RAM. Two files matter per story:

  • board/stories/<issue_id>.json — the story: state, points, votes, assignee, commit_sha, files_to_touch, depends_on, sprint_number.
  • board/audit/<issue_id>.jsonl — append-only trail of every state transition and decision.

State machine:

  draft ──► refinement ──► ready ──► in_progress ──► review ──► pending_acceptance ──► done
                                                        │              │                  │
                                                        └─────────► blocked ◄─────────────┘

Concurrency

BoardStore.try_claim_next_for(role, actor, sprint_number) is atomic under a threading.Lock. It filters candidates by:

  1. state == ready
  2. type matches worker (architect ← architecture/feature; test ← test; devsecops ← security)
  3. all depends_on stories are done (real Scrum DoD)
  4. if sprint_number > 0: story's sprint_number matches (Sprint Backlog commitment)
  5. files_to_touch doesn't overlap with any in-flight story's files (prevents parallel-work collisions)

Single-process safety only — the whole async runtime is one asyncio loop. Cross-process sharing isn't supported by design.

5. Merge queue — rebase-before-merge, blocked on conflict

Every successful commit an agent lands is enqueued, not merged directly. A single run_merge_worker coroutine drains the FIFO queue serially under an asyncio.Lock.

  agent's worktree              integration worktree
  (branch: team/X/agent/Y)      (branch: team/X/integration)
      │                                  │
      │  agent commits new SHA           │
      ├──► MergeQueue.enqueue(request) ──┤
      │                                  │
      │                              worker:
      │                              1. rebase agent branch onto integration
      │                                 (inside AGENT worktree — that's where the
      │                                 branch is checked out; git refuses to
      │                                 check it out twice)
      │                              2. checkout integration
      │                              3. merge --ff-only agent branch
      │                              4. transition story → pending_acceptance
      │
      │  on conflict during rebase:
      │  → abort rebase
      │  → transition story → blocked
      │  → reason: "merge_conflict:<git stderr>"

git rerere is enabled in every worktree so recurring conflict resolutions carry forward. There's no LLM-based conflict auto-resolution — a real conflict is genuine ambiguity that the human PO should resolve.

6. Sprints, DoD, PO acceptance — the real-Scrum layer

Three additions that separate v2 from "just Kanban with ceremonies":

Definition of Done — paired test subtasks

The PO decomposer prompt requires every feature/architecture/security story that ships production code to be paired with a test story with depends_on: [parent_index]. The test can't be pulled until the parent is done — enforcing that testing is part of the story's DoD.

Sprints — commitment + boundary

  sprint 0 (bootstrap)     — first backlog decomposed, no sprint yet
    │
    ▼   SM's sprint_boundary ceremony fires
  sprint 1 opens:
    - PO selects up to velocity_target ready stories
    - each gets sprint_number = 1
    - other ready stories stay sprint_number = 0 (not pullable)
    │
    ▼   next boundary fires
  sprint 2 opens:
    - previous sprint auto-closes (populates stories_done, points_completed)
    - PO selects next N ready stories → sprint_number = 2
    - and so on

Each sprint is a JSON file at <workspace>/sprints/<n>.json with started_at, ended_at, committed_backlog, stories_done, points_completed.

PO Acceptance gate — the DoD checkpoint

Merge worker no longer transitions merged stories directly to done. Instead → pending_acceptance. The PO's 1-minute HEARTBEAT action _run_acceptance reviews pending stories and either accepts (→ done) or rejects (→ blocked with reason). Mirrors real Scrum where PO is the single voice deciding whether work meets acceptance criteria.

7. Ceremonies — heartbeat-scheduled meetings

No standups. No calendar. Each agent's HEARTBEAT.md declares its own schedule, parsed by HeartbeatScheduler:

# PO HEARTBEAT.md
## Every 1 minutes
Acceptance review: for each story in pending_acceptance state, accept or reject.

## Every 30 minutes
If ready backlog < 3 stories, invoke replan(): read SPEC.md and RETRO.md.

## Every 60 minutes
Poll PR comments via pr_feedback.ingest().

The scheduler emits ScheduledTask(cadence_seconds, action_text)s at their cadence. AsyncAgent.loop routes each task's action_text to the matching ceremony method via word-boundary keyword match — replan → _run_replan, retrospective → _run_retro, sprint + open/close/planning → _run_sprint_boundary, accept/acceptance → _run_acceptance, poker/refinement → _run_poker, pr + comment/review → _run_pr_feedback.

8. Supervisor — crash recovery

TeamSupervisor spawns all 5 agents as tasks and watches for exceptions. Exponential backoff on restart: 5s → 30s → 5min → 30min → 60min. Emits agent_crashed/agent_restarted events. Restart preserves the same agent instance (state carries across). Scheduler markers are reset on loop re-entry so long-cadence tasks don't freeze after a crash.

9. Spawn/governance substrate — permission tiers, audit, rubric

Everything above delegates individual agent invocations to orgos.spawn.spawn(role, brief). Spawn is the safety fabric — it's what prevents a Worker-tier agent from silently gaining publish-class tools, what makes malformed output → needs_revision, what writes the audit trail every tool call lands in.

             │                                            │
             │  RoleSpec ──► tier enforcement ──► tools   │
             │  TaskBrief ──► boundaries + budget ──► task│
             │                                            │
             │  ┌─────────────────────────────────────┐  │
             │  │  PERMISSION TIERS (enforced in code) │  │
             │  │  ─────────────────────────────────── │  │
             │  │  worker      compute only, no publish│  │
             │  │  validator   review + gate           │  │

             │  └─────────────────────────────────────┘  │
             │                                            │
             │  ┌─────────────────────────────────────┐  │
             │  │  AUDIT TRAIL (every run)             │  │
             │  │  _audit_logs/<run_id>.jsonl          │  │

             │                                            │
             └───────────────────────────────────────────┘

Key guarantees (from docs/spawn-rubric.md)

GuaranteeEnforced by
Worker can't publish_enforce_tier rejects publish-category tools at load time (no tokens spent)
Publisher needs human gate_wire_gates — no approval_fn → _TierViolation
Bad output ≠ accepted_read_envelope: non-JSON / empty / missing criteria → needs_revision
Worker never grades itselfRubric grader is a separate function or agent
Max attempts = fail closed_exhausted overrides envelope to needs_revision
Everything is logged_audit_logs/<run_id>.jsonl
Off-limits: agents cannot modify orgos/spawn/ — this is enforced by the platform, not by prompting. This is the trust boundary that lets us hand a coding agent significant power without giving it the power to change its own governance.

10. Waterfall topology — the comparison baseline

Same PO decomposition. But there is no board, no refinement, no wiki. Every story runs through Architect → Test → DevSecOps sequentially on the shared integration worktree.

  PO decomposes → list of stories
       │
       ▼
  for each story (in priority order):
    Architect  → writes code → commits
    Test       → verifies commit → runs pytest
    DevSecOps  → reads diff → checks for secrets / oversized diff / governance violations
    Release manager  → optional PR publisher
       │
       ▼
  → campaign_result.json (stories_done, tokens, wall time, ...)

This is the topology an LLM produces by default when you ask it for "an agentic dev team." Included as the baseline to beat — see comparison.html for the head-to-head.
